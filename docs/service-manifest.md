# Манифест сервиса для pulse

Стандарт, по которому сервис сам рассказывает pulse о себе, о своём состоянии и о своих
диагностических ручках. pulse находит манифест сам, проверяет его и отдаёт агенту (LLM) —
тот отвечает людям на вопросы вроде «что с доставкой», «почему не проходит заказ 234115».

Версия стандарта: **1**.

Стандарт **не зависит от языка и фреймворка**: это несколько HTTP-ручек, отдающих JSON. Go-сервисам
на gotemplate реализацию даёт готовый модуль шаблона; на любом другом стеке ручки пишутся по
этому документу (или выносятся в общую библиотеку своего стека).

> **Если вы агент, которого попросили реализовать это в сервисе**, — начните с раздела
> «Для агента, который реализует стандарт в сервисе»: сначала изучите сервис, потом
> спросите у разработчика недостающее, предлагая варианты.

---

## Коротко

Сервис на своём **служебном порту** — отдельном внутреннем HTTP-порту, закрытом снаружи (см.
«Куда смотреть: порт и путь»), — отдаёт:

| Ручка | Что это | Обязательна |
|---|---|---|
| `GET /.well-known/pulse` | **манифест**: кто я, чья команда, как меня мониторить, какие у меня диагностические ручки | да |
| `GET /.well-known/pulse/status` | **состояние**: мои зависимости (БД, Kafka, внешние API) — ok / degraded / down | нет, но очень желательна |
| диагностические ручки | ответы на конкретные вопросы: «где заказ N в конвейере», «сколько в очереди» | нет |

Главное правило безопасности — **pulse пропускает только объявленное**: всё, что сервис
вернул, но не описал в схеме ответа в манифесте, pulse вырезает. Подробно — в разделе
«Конфиденциальность».

Go-сервисам на gotemplate всё это даёт готовый модуль шаблона (см. в конце) — руками пишутся
только сами диагностические ручки. Остальные стеки реализуют те же ручки сами.

## Для агента, который реализует стандарт в сервисе

Этот документ обычно читает не человек, а агент (Claude Code и т. п.) по просьбе разработчика
«сделай манифест pulse». Прежде чем спрашивать разработчика о тонкостях, загляни в «Частые
вопросы» в конце документа. Агент, порядок такой:

### 1. Сначала изучи сервис сам — не спрашивай того, что есть в коде

| Что узнать | Где искать |
|---|---|
| стек | язык и фреймворк: `go.mod`, `package.json`, `pyproject.toml`/`requirements.txt`, `composer.json`, `pom.xml`/`build.gradle`, Dockerfile |
| имя, назначение | имя репозитория, README, CLAUDE.md, описание в GitHub, названия доменных сущностей |
| зависимости (`dependencies`) | где создаются клиенты БД, кэшей, брокеров, HTTP/gRPC-клиенты: точка сборки приложения (Go — `internal/app/app.go`; Node — `main.ts`/`app.module.ts`/`index.js`; Python — `main.py`/`settings.py`/фабрика приложения; PHP — сервис-провайдеры и `config/`; Java — `@Configuration`/`application.yml`), список зависимостей пакетного менеджера (драйверы postgres, redis, kafka), конфиг и пример окружения (**только имена переменных**), чарт в helm-репозитории (`charts/<сервис>` — env, sidecar'ы) |
| куда ведёт зависимость (`target`) | имена переменных адресов (`*_URL`, `*_HOST`) и значения по умолчанию в коде; у внутренних сервисов — имя k8s Service |
| служебный порт | есть ли у сервиса второй HTTP-порт (у gotemplate — `SYSTEM_HTTP_PORT`, 3003), `containerPorts` в чарте, где сейчас отдаются `/healthcheck` и `/metrics` |
| `build` | как в образ попадает версия: Go — ldflags; остальные — `ARG`/`ENV` в Dockerfile из переменных CI (`GITHUB_SHA`, тег) — туда же добавь коммит и время сборки |
| свои метрики | регистрация Prometheus-метрик: Go — `promauto`/`NewCounterVec`; Node — `prom-client`; Python — `prometheus_client`; Java — Micrometer; PHP — `promphp` |
| кандидаты в диагностические ручки | доменные сущности со статусами и жизненным циклом (заказ, задача, платёж), очереди/outbox, фоновые синхронизации и их «последний запуск», фичефлаги |
| отчёт по объектам (`entities` ручки состояния) | таблица объекта и колонки статуса и времени смены статуса (`status`, `updated_at`/`status_changed_at`), есть ли по ним индекс — счётчики считаются одним `GROUP BY status` |
| `domain` | за что отвечает — use case'ы и обработчики; объекты — доменные модели; формат номера — тип и генерация id (последовательность, префикс, длина; в тесте — пример); статусы — enum/константы и переходы между ними; чем не занимается — какие вызовы уходят в соседние сервисы (оплата → payments) |
| что опасно | поля сущностей с ФИО/телефоном/адресом/комментариями, ошибки драйверов, которые где-то возвращаются как есть |

**Секреты не читай**: ни `.env`, ни значения секретов в кластере, ни `values/` helm-репозиториев.
Для манифеста нужны только имена переменных и хосты, не значения.

### 2. Покажи разработчику черновик и спроси только недостающее — с подсказками

Собери черновик манифеста из найденного и покажи его целиком. Затем задай вопросы — **каждый
с твоим предложением**, чтобы разработчику оставалось подтвердить или поправить:

| Вопрос | Почему из кода не узнать | Как подсказать |
|---|---|---|
| `title`, `description` | нужен человеческий язык, а не имена пакетов | предложи формулировку по доменным сущностям: «Принимает заказы… и ведёт их до выдачи» |
| `aliases` | как сервис называют люди, знает только человек | предложи: транслитерация, русское название, аббревиатура, старое имя репозитория |
| `owner.team`, `owner.contacts` | в коде этого нет | предложи команду по CODEOWNERS / авторам коммитов, но **не выдумывай** — спроси. Контакты — чат или почта команды, не личные телефоны |
| `criticality` | зависит от бизнеса | предложи по смыслу (принимает заказы/платежи → `high`) и объясни выбор одной фразой |
| `critical` у зависимостей | без какой сервис не работает, а без какой — деградирует | предложи: основная БД — `true`, внешние API с повторами/кэшем — `false` |
| `affects` у зависимостей | что ломается для бизнеса | предложи по коду: где клиент зависимости используется — «bank → онлайн-оплата» |
| какие диагностические ручки нужны | зависит от того, о чём спрашивают дежурные | предложи 2–3 из кандидатов с обоснованием: «часто спрашивают, где заказ — ручка `order_status`» |
| какие поля ответа отдавать | граница конфиденциальности — решение человека | по каждой ручке покажи поля: что предлагаешь отдать, что пометить `x-personal` (и каким видом: `phone`, `email`…), что убрать — и почему |
| `domain` | смысл статусов, «когда застрял», границы ответственности — знание людей | покажи черновик из кода: объекты с форматом номера, статусы с твоей трактовкой, `stuck_after` — предложи по смыслу («assigned → 30m: курьер обычно выезжает за 15 минут») и попроси поправить |
| `runbooks`, `docs_url` | ссылки на вики | спроси, есть ли; нет — пропусти |

**Порядок вопросов.** Интерфейс агента обычно позволяет задать не больше 4 вопросов за раз —
задавай пачками по важности, а не одним длинным списком:

1. `owner.team` и `criticality`; какие диагностические ручки нужны — без этого нечего строить;
2. какие поля ручек отдавать и какие из них персональные; `critical` и `affects` зависимостей;
   `domain` — подтвердить черновик: смысл статусов, `stuck_after`, чем сервис не занимается;
   сколько застрявших объектов — уже проблема (`degraded` в отчёте по объектам);
3. `owner.contacts`, `runbooks`, `docs_url` — можно пропустить, если разработчик не знает.

`title`, `description` и `aliases` отдельным вопросом не задавай: предложи их в черновике — их
поправят, если что-то не так. Не заполняй неизвестное правдоподобными выдумками: команда и
контакты, придуманные агентом, хуже пустого поля.

**Что увидит человек, если поле персональное.** Разработчик обязательно спросит «увижу ли я
настоящий номер». Ответ: модель видит вместо значения токен (`pii:phone:…`) и по нему ищет
дальше, а человек в итоговом ответе агента (Telegram, service desk) получает **настоящее
значение** — токены раскрывает pulse_agent после модели. Поэтому `x-personal` не мешает
диспетчеру: поля вроде `phone_last4` для этого не нужны.

### 3. Реализуй

- Go на gotemplate — через модуль шаблона (раздел «Go: модуль в gotemplate»). Любой другой
  стек — по разделам ниже, средствами своего фреймворка: второй HTTP-сервер на служебном порту,
  фоновая задача для проверок зависимостей, схема ответа — из тех же типов, что сериализуют
  ответ, если стек это умеет (pydantic, zod, OpenAPI-генераторы), иначе — руками.
- Нет служебного порта — заведи его (см. «Куда смотреть: порт и путь»); если разработчик
  против — объясни риск и закрой пути на ingress.
- Сообщения о состоянии зависимостей — свои короткие формулировки, не текст исключения как есть.
- Диагностические ручки — только чтение, с индексом и `LIMIT`, в пределах таймаута.

### 4. Проверь сам и отчитайся

- Запусти сервис локально и получи `GET /.well-known/pulse` и `/.well-known/pulse/status` —
  JSON валиден, поля по этому документу.
- Убедись, что pulse найдёт порт (раздел «Куда смотреть: порт и путь»): манифест на том же
  порту, что и `/metrics`, или порт назван `system` (у контейнера или в k8s Service), или у пода
  есть аннотация `pulse/port`.
  Если ничего из этого нет — предложи разработчику аннотацию в чарте.
- Вызови каждую диагностическую ручку и сверь ответ со схемой: **в ответе не должно быть полей,
  которых нет в схеме** (pulse их всё равно вырежет, но это значит, что ручка отдаёт лишнее).
- Сверь цифры: одно и то же число в `entities`, показателях и ручках совпадает (правило «Одна
  цифра — в одном месте» в разделе «Состояние»).
- Пройди чек-лист из раздела «Конфиденциальность» и покажи разработчику результат по пунктам.
- В итоге перечисли, что спросил у разработчика и что заполнил сам по коду, — чтобы на ревью
  было видно, где решения человека.

## Зачем

- **Каталог без ручного заполнения.** Название, команда, критичность, синонимы — у сервиса,
  в коде, рядом с тем, что они описывают. Меняется вместе с кодом, не устаревает.
- **Причина, а не симптом.** Метрики показывают «caravan тормозит». Ручка состояния
  показывает «потому что 1С отвечает 4 секунды». Агент видит это сразу в снапшоте сервиса.
- **Вопросы о бизнес-объектах.** По логам «что с заказом 234115» восстанавливается долго и
  не всегда. Диагностическая ручка сервиса знает ответ точно.
- **Точный коммит в проде.** Сервис сам сообщает, из какого коммита собран, — pulse больше
  не нужно угадывать это по реестру образов и запускам CI.

## Куда смотреть: порт и путь

- Манифест и все ручки из него — **на одном служебном порту**: отдельном HTTP-порту для
  внутренних нужд (здоровье, метрики, диагностика). У gotemplate он уже есть —
  `SYSTEM_HTTP_PORT` (по умолчанию `3003`). В других стеках это второй HTTP-сервер в том же
  процессе — несколько строк в любом фреймворке (Express/Fastify, FastAPI/Flask, Spring
  `management.server.port`, отдельный `server` в nginx).
- Служебный порт **не публикуется наружу** (в ruto и ingress идёт только основной HTTP-порт).
  Это часть модели безопасности: ручки доступны только изнутри кластера.
- **Если отдельного порта сделать нельзя** (у сервиса один порт), ручки допустимы на основном
  порту, но тогда пути `/.well-known/pulse*` и диагностических ручек обязаны быть **закрыты
  снаружи**: не опубликованы в ruto и отрезаны на ingress (у ingress с маршрутизацией по
  префиксу `/` они иначе окажутся в интернете). Это пункт ревью — лучше всё-таки порт.
- **Как pulse находит порт.** Специально называть порты не обязательно — pulse пробует по
  порядку, пока не получит манифест:
  1. аннотация пода `pulse/port: "8081"` (и при необходимости `pulse/path` — другой путь
     манифеста) — надёжнее всего, подходит любому стеку;
  2. **порт, с которого Prometheus собирает `/metrics` у этого пода** (цели Prometheus): по
     стандарту манифест живёт на том же служебном порту, что и метрики, — так порт находится
     без всяких имён;
  3. порт с именем `system`, затем `http` / `http-*` — у контейнера (`containerPort`) или у
     k8s Service, который выбирает под (номер берётся из `targetPort`);
  4. порты по умолчанию из правил pulse (`manifest.default_ports`, у нас — `3003`);
  5. в крайнем случае — остальные порты пода (`containerPorts`, а если их нет — порты k8s
     Service, который указывает на под), **кроме заведомо не-HTTP** (5432, 6379, 9092, 3306,
     5672, 27017, 2181, 9000 и т. п.). Этот шаг — один раз после выкатки, таймаут 1 с на
     порт: лишний HTTP-запрос в чужой порт ничего не ломает, но может оставить строку ошибки
     в логе, поэтому он последний и редкий.

  Найденный порт pulse запоминает до следующей выкатки. Не нашёл — в каталоге статус `absent`
  или `unreachable` и **список портов, которые пробовал**: владельцу остаётся поставить
  аннотацию `pulse/port`.
- pulse ходит **в под напрямую** (по IP пода), а не через k8s Service: служебного порта в
  Service обычно нет, а состояние у каждого пода своё.
- **Сервис без своего кода** (фронтенд на nginx, сторонний образ): манифест можно отдать
  статическим JSON-файлом (`location = /.well-known/pulse` в отдельном `server` nginx), без
  ручки состояния и диагностических ручек. Или описать сервис в `service.yaml` в репозитории.

## Как pulse находит манифест

1. Индексер pulse обходит кластер (раз в несколько минут). Для каждого workload'а сервиса он
   берёт один готовый (Ready) под и делает `GET http://<ip пода>:<порт>/.well-known/pulse`.
2. Запрос повторяется, когда:
   - сменился образ (новый digest — была выкатка);
   - прошлый успешный ответ старше суток;
   - прошлая попытка неудачна и старше часа.

   В остальное время pulse берёт манифест из своего кэша — сервис не получает лишней нагрузки.
3. Итог для каждого сервиса виден в каталоге (`list_services`, `get_service_info`):

   | Статус | Значит |
   |---|---|
   | `ok` | манифест принят |
   | `partial` | манифест принят, но часть его отклонена (например, одна ручка) — причины перечислены |
   | `invalid` | манифест не принят целиком — причина указана |
   | `absent` | порт отвечает, но манифеста нет: 404 или ответ без поля `pulse_manifest` (SPA и catch-all отдают `200` на любой путь — это не манифест) |
   | `unreachable` | порт не отвечает (или нет готовых подов) |

   Это же — отчёт о покрытии: у каких сервисов стандарт уже есть и у кого он с ошибками.

**Приоритет источников.** Манифест важнее `service.yaml` в репозитории: если манифест принят,
`service.yaml` не читается. `service.yaml` остаётся для случаев, когда отдавать манифест
некому (сторонние образы) или манифест ещё не сделан. Диагностические ручки — **только из манифеста**.

**Что считается одним сервисом.** pulse собирает workload'ы в сервис **по репозиторию образа**:
все Deployment/StatefulSet/CronJob с образами из одного репозитория (`ghcr.io/org/caravan`,
`ghcr.io/org/caravan/worker`) — один сервис. Чарт тут ни при чём: фронтенд из своего
репозитория, отдельный продукт (herder) и Postgres в том же чарте — **отдельные сервисы** со
своими манифестами (или без них); Postgres, Redis и другие сторонние образы — отдельные сервисы
без манифеста. Совпадать раздел `service` должен только у workload'ов одного репозитория.

**Несколько workload'ов у сервиса** (например, `loom/server` и `loom/artifact`): каждый
отдаёт свой манифест. Раздел `service` у них должен совпадать; `id` ручек — уникальны в
пределах сервиса (pulse запоминает, какой workload обслуживает какую ручку). Противоречие —
`partial` с причиной.

## Общие требования к ручкам

- Только `GET`, **без побочных эффектов**: вызов ничего не меняет, не ставит в очередь, не
  шлёт уведомлений. pulse другими методами не ходит.
- Ответ — `application/json; charset=utf-8`, UTF-8. Другой тип ответа pulse не принимает.
- Ответ за **≤ 2 с** (манифест, состояние) и за **≤ 5 с** (диагностические ручки). pulse
  обрывает запрос по таймауту из манифеста, но не дольше 10 с.
- Размер ответа — **≤ 256 KB**. Больше — pulse обрезает и помечает ответ как усечённый.
- Без редиректов (pulse им не следует).
- Время — RFC 3339 со смещением (`2026-09-25T19:07:41+05:00`; UTC — `2026-09-25T14:07:41Z`,
  это тоже смещение); длительности — числом в миллисекундах (`latency_ms`); размеры — в байтах.
- `null` у любого поля ответа — «нет значения» (заказ ещё не отгружен — `shipped_at: null`); pulse
  пропускает его как есть. Необъявленное поле `null` не спасает — оно вырезается.
- Ошибка — HTTP-статус 4xx/5xx и тело `{"error": "что пошло не так"}`. Текст ошибки уходит
  агенту (после маскировки), поэтому пишите его для человека: «заказ не найден», а не стек.
- pulse передаёт в каждом запросе заголовки:
  - `User-Agent: pulse/<версия>`;
  - `X-Pulse-Request-Id: <id>` — **пишите его в свой лог** вместе с параметрами: по нему
    вызов связывается с журналом вопросов агента (кто спросил, что и зачем).
- Нагрузка: pulse вызывает ручки только по запросу агента (и состояние — при построении
  снапшота сервиса), не больше 2 одновременных запросов к одному сервису, ответ состояния
  кэширует на 15 с. Фоновых опросов нет.

### Поля

**Верхний уровень**

| Поле | Обяз. | Описание |
|---|---|---|
| `pulse_manifest` | да | версия стандарта, сейчас `1`. pulse понимает текущую и предыдущую версии; неизвестная — `invalid` |
| `service` | да | кто я |
| `build` | нет | из чего собран этот экземпляр |
| `runbooks` | нет | инструкции для дежурных |
| `dependencies` | нет | от чего я завишу — основа для ручки состояния и графа зависимостей |
| `metrics` | нет | свои метрики, если стандартных (rps, ошибки, задержка) недостаточно |
| `logs` | нет | свой селектор логов и узнаваемые ошибки |
| `domain` | нет, но очень желательно | бизнес-смысл: за что отвечаю и что нет, мои объекты (формат номера, статусы, когда застрял), типичные вопросы ко мне |
| `endpoints` | нет | диагностические ручки |

Неизвестные поля pulse игнорирует — так новые версии стандарта не ломают старый pulse.

**`service`**

| Поле | Обяз. | Описание |
|---|---|---|
| `name` | да | имя в каталоге: `^[a-z0-9][a-z0-9_-]{0,62}$`. Обычно совпадает с именем репозитория. Если другое — каталог переименует сервис; два сервиса с одним именем — `invalid` у второго |
| `title` | да | человеческое название, ≤ 100 символов |
| `description` | да | что делает сервис, ≤ 500 символов. Пишите так, чтобы по описанию можно было найти сервис: «принимает заказы…», а не «микросервис на Go» |
| `aliases` | нет | как ещё называют сервис люди — по-русски, сокращения, старые имена (≤ 20) |
| `owner.team` | да | команда-владелец (одно имя, одинаково во всех сервисах команды) |
| `owner.contacts` | нет | куда писать: чат, дежурный, почта команды. **Не личные телефоны** |
| `criticality` | да | `high` — без него не работают продажи/выдача; `medium` — деградация заметна клиентам; `low` — внутреннее |
| `repo_url`, `docs_url` | нет | ссылки |

**`build`** — задаётся при сборке, не руками: Go — ldflags; остальные — `ARG`/`ENV` в
Dockerfile из переменных CI (`GITHUB_SHA`, тег релиза), которые сервис читает на старте.

| Поле | Описание |
|---|---|
| `version` | версия/тег сборки |
| `commit` | полный SHA коммита — pulse берёт его как коммит в проде в первую очередь |
| `built_at` | время сборки |

**`dependencies[]`**

| Поле | Обяз. | Описание |
|---|---|---|
| `id` | да | `^[a-z][a-z0-9_]{0,40}$`, на него ссылается ручка состояния |
| `kind` | да | `postgres`, `redis`, `kafka`, `rabbitmq`, `clickhouse`, `elasticsearch`, `s3`, `http`, `grpc`, `other` |
| `target` | да | **куда** — имя сервиса в кластере (`ocenter-pg`) или внешний хост (`api.bank.kz`). **Без логинов, паролей, строк подключения и порта** — только имя: по нему pulse находит сервис в кластере для графа зависимостей |
| `critical` | да | `true` — без неё сервис не работает (её `down` делает весь сервис `down`) |
| `affects` | нет | **что ломается**, когда она недоступна, словами владельца (≤ 100): «выдача заказов», «онлайн-оплата». `critical` отвечает только на «весь сервис лежит или нет»; `affects` агент назовёт человеку: «bank down — ломает онлайн-оплату» |

Объявляется то, что **настроено в этом окружении**: интеграция выключена (адрес не задан) —
зависимости нет и в манифесте. Один и тот же образ в разных окружениях может отдавать разный
состав зависимостей — это нормально: pulse читает манифест каждого workload'а отдельно.

**Как проверять зависимость.** Проверка должна отвечать на «работает ли она для нас», а не
«жив ли порт», и ничего не стоить:

| Зависимость | Проверка |
|---|---|
| БД, кэш, брокер | ping клиента (`SELECT 1`, `PING`, metadata-запрос) — дёшево и честно |
| внутренний HTTP/gRPC-сервис | его `/healthcheck` или gRPC health, если есть; иначе — `/.well-known/pulse/status` |
| внешний API с бесплатной ручкой | ручка статуса или проверки ключа (`/ping`, `/me`, `/status`) — честно и про авторизацию |
| внутренний gRPC-сервис | gRPC health через **отдельное соединение без перехватчиков** клиента — иначе проверка попадёт в метрики внешних вызовов и в пассивные проверки; `Unimplemented` значит «health не реализован», а не «сервис лежит». Проще — состояние соединения клиента (`READY`/`TRANSIENT_FAILURE`) |
| **платный API, API с лимитами, без health-ручки** | **пассивная проверка**: сервис запоминает исходы своих настоящих вызовов за окно (5 мин); все последние (от трёх подряд) неудачны — `down`, неудачных больше половины — `degraded`, вызовов не было — `ok` (не с чем сравнить). Проверочный запрос не тратит деньги и квоту. **Сбой — зависимость не сделала свою работу для сервиса**: сеть, 5xx, а также отказы, которые значат поломку интеграции (401/403 — ключ, 429 — квота, 400 на запрос, который сервис должен формировать правильно). Штатный ответ, даже отказ по делу (404 геокодера на плохой адрес, повторный capture), — не сбой. Решает сервис по смыслу. Без вызовов — `ok` с пометкой «вызовов не было». В pulsekit — `pulsekit.NewPassive` |
| **редкий критичный вызов** (брокер оплаты вызывается только при выдаче) | пассивная проверка + TCP: были вызовы — судит пассивная; не было (`Passive.Idle()`) — TCP, статус `ok` с пометкой «вызовов не было, сеть до хоста есть» (у `ok` пометка допустима). Образец — `ExamplePassive_Idle` |
| ничего из этого | TCP-соединение с хостом — только в крайнем случае: оно честно лишь про сеть, а не про то, что API отвечает и принимает ключ. Сообщение так и пишите: «сеть до хоста есть» |

**`metrics[]`** — как в `service.yaml`: `id`, `title`, `promql`, `unit` (`count`, `ratio`,
`seconds`, `bytes`, `rps`), `direction` (`higher_is_better` / `lower_is_better`). Плейсхолдеры
`{namespace}`, `{pod_regex}`, `{service}` подставляет pulse. Всё остальное, что знает только
сервис (префикс имён метрик из `METRICS_NAMESPACE` и т. п.), сервис подставляет сам: манифест
строится при запуске, PromQL — обычная строка.

**`logs`** — `selector` (LogQL, если стандартный по namespace/подам не подходит) и
`error_patterns[]` (`name`, `pattern` — регэксп в синтаксисе RE2: без lookahead и обратных
ссылок, его исполняет pulse): узнаваемые ошибки, которые агент назовёт по имени.

**`domain`** — бизнес-смысл сервиса для агента. Без него агент знает, *что* сервис делает, но
не понимает его данных: чей номер «7784512», нормально ли `status: assigned` через два часа, в
каком сервисе искать причину, если этот ни при чём. Уходит модели при каждом `get_service_info`,
поэтому коротко:

| Поле | Описание |
|---|---|
| `responsibilities[]` | за что сервис отвечает — до 5 пунктов по 200 символов, глаголами: «назначает курьера на доставку» |
| `not_responsible[]` | чем **не** занимается и кто занимается: `what`, `service` (имя в каталоге) — агент пойдёт искать причину туда, до 10 |
| `entities[]` | бизнес-объекты, до 10: `name`; `id_pattern` — формат номера (RE2 на всё значение: `[0-9]{7}`) и `id_example` (должен подходить) — по ним агент узнаёт объект в вопросе, а pulse подсказывает в поиске по логам, чей это номер (`id_matches`); `description`; `statuses[]` — `name`, `meaning` (одной строкой), `stuck_after` (`30m`, `2h` — дольше в этом статусе объект застрял; нет — не застревает), до 20 |
| `questions[]` | типичные вопросы к сервису и куда за ответом, до 10: `question`, `endpoint` (id ручки из этого манифеста) или `how` словами («логи сервиса по номеру доставки») |

Ошибки в `domain` не отменяют манифест: лишнее отбрасывается с причиной (`partial`), неверный
`id_pattern` или пример не по нему — шаблон не принимается, ссылка на необъявленную ручку —
отбрасывается.

**`endpoints[]`** — диагностические ручки, см. ниже.

### Лимиты манифеста

Манифест ≤ 64 KB; ручек ≤ 30; параметров у ручки ≤ 10; зависимостей ≤ 30; метрик ≤ 20;
вложенность схемы ответа ≤ 6 уровней. Превышение — `invalid` (для манифеста) или отказ ручке
(`partial`). Тексты: названия (`title`) ≤ 100 символов, описания (`description`) ≤ 500,
описание ручки — ≤ 1000 (на нём держится выбор агента). Лимит мягкий: длиннее pulse обрезает и
пишет причину в каталоге — описания уходят модели при каждом вопросе, и длинное описание обычно
значит, что в него пишут не то (перечень значений — это `enum`).

## Состояние: `GET /.well-known/pulse/status`

Отвечает на вопрос «здоров ли я и если нет — из-за чего». pulse кладёт ответ в снапшот
сервиса: агент видит причину без дополнительных вызовов.

```json
{
  "status": "degraded",
  "checked_at": "2026-09-25T19:07:40+05:00",
  "dependencies": [
    { "id": "pg", "status": "ok", "latency_ms": 3 },
    { "id": "kafka", "status": "ok", "latency_ms": 12 },
    { "id": "onec", "status": "degraded", "latency_ms": 4200, "message": "ответ дольше 2 с (порог)" }
  ],
  "gauges": [
    { "id": "outbox_backlog", "title": "Неотправленные события", "value": 1840, "unit": "count", "status": "degraded" },
    { "id": "last_1c_sync", "title": "Последняя выгрузка в 1С", "value": "2026-09-25T18:52:00+05:00", "unit": "time", "status": "ok" }
  ],
  "entities": [
    {
      "name": "заказ",
      "status": "ok",
      "statuses": [
        { "name": "new", "count": 12 },
        { "name": "paid", "count": 42, "stuck": 3, "oldest_s": 10800 },
        { "name": "assembling", "count": 17 }
      ],
      "created_1h": 120,
      "finished_1h": 110
    }
  ]
}
```

| Поле | Описание |
|---|---|
| `status` | итог: `ok` / `degraded` / `down`. `down` — если `down` хотя бы одна `critical`-зависимость; `degraded` — если деградировало что-то ещё |
| `checked_at` | когда проверки выполнялись на самом деле |
| `dependencies[]` | по одной записи на каждую зависимость из манифеста: `id`, `status`, `latency_ms`, `message` (≤ 300 символов: у не-`ok` — причина, у `ok` — необязательная пометка вроде «вызовов не было, сеть до хоста есть») |
| `gauges[]` | несколько показателей, которых нет в метриках и которые объясняют состояние: `id`, `title`, `value` (число или время), `unit`, `status` (≤ 20 штук) |
| `entities[]` | **как сервис работает по сути** — объекты из `domain` манифеста (≤ 10): `name` (как в `domain`), `status`, `statuses[]` — `name`, `count` (сейчас в статусе), `stuck` (из них дольше `stuck_after` статуса в `domain`), `oldest_s` (сколько секунд в текущем статусе — не с создания — самый старый, необязательно; по тем же записям, что `stuck`: кто ждёт намеренно — перенесён, отложен — не в `stuck` и не в `oldest_s`, иначе «самый старый — 4 дня» при «застрявших 0» читается как противоречие); `created_1h`, `finished_1h` — поток за час (необязательно). Считается в фоне вместе с проверками. Объекты, которых нет в `domain`, pulse не показывает |

**Зачем `entities`.** Зависимости и показатели отвечают на «здоров ли сервис технически».
Объекты — на «работает ли он по сути»: «доставки идут, застряло 3 из 42 в assigned (дольше 30
мин)». Порог застревания объявлен один раз в `domain` (`stuck_after`), ручка отдаёт только
счётчики — одним запросом к своей БД с группировкой по статусу. Когда застрявших много, сервис
сам ставит объекту (и себе) `degraded` — порог «много» выбирает владелец. pulse показывает это
агенту в снапшоте: «сервис сообщает: застряло 12 из 42 «доставка» в статусе assigned (курьер
назначен) — дольше 30 мин, самый старый — 1.5 ч».

**Одна цифра — в одном месте.** Если одно и то же число видно в нескольких местах — в
`entities`, в показателе (`gauges`) и в диагностической ручке («сколько в работе», «сколько
застряло», «самый старый»), — оно везде должно быть одинаковым: считается одним запросом (одной
функцией репозитория) с одними правилами — какие записи живые, кто ждёт намеренно, время в
статусе или с создания. Ручка не пересчитывает то, что уже есть в `entities`, по-своему: она
даёт подробности (разбивку, примеры, причины) поверх тех же счётчиков. Иначе агент получит
«16 290 в работе» из ручки и «1 500» из отчёта и не поймёт, чему верить. То, что в счётчики не
входит намеренно (брошенные, отложенные), — отдельной цифрой с понятным названием.

Тонкости:

- **Не проверяйте зависимости на каждый запрос.** Проверки идут в фоне (раз в 15–30 с), ручка
  отдаёт последний результат. Иначе опрос состояния сам становится нагрузкой, а медленная
  зависимость делает медленной и ручку.
- **Это не liveness.** `/healthcheck` отвечает «процесс жив» и не зависит от БД — иначе k8s
  начнёт перезапускать все поды, когда упадёт база. `/.well-known/pulse/status` — только для
  диагностики, в пробы его не подключать.
- Состояние — **этого экземпляра** (пода). pulse опрашивает до 3 готовых подов и показывает
  худший результат с указанием пода.
- **`message` — самое опасное поле.** Драйверы кладут в текст ошибки строку подключения,
  иногда с паролем (`postgres://user:pass@host`), SQL с данными, адрес запроса с токеном в
  query. Пишите своё короткое сообщение («таймаут подключения», «отказ в авторизации»), а не
  текст исключения как есть (`err.Error()`, `str(e)`, `e.message`, `getMessage()`). pulse дополнительно вырезает `user:pass@` из URL и маскирует
  телефоны/почту/карты, но это страховка, а не решение.

## Диагностические ручки

Ручка отвечает на один понятный вопрос о работе сервиса. Хорошие примеры:

- «Где заказ N в конвейере и почему застрял» — статус, история статусов, шаг, причина.
- «Что в очереди отправки» — сколько, самое старое, распределение по причинам.
- «Когда и как прошла последняя синхронизация с X» — время, сколько записей, ошибки.
- «Какие фичефлаги сейчас включены» — имена и значения.

### Описание ручки в манифесте

| Поле | Обяз. | Описание |
|---|---|---|
| `id` | да | `^[a-z][a-z0-9_]{0,40}$`, по нему агент вызывает ручку |
| `title` | да | ≤ 100 символов |
| `description` | да | **для агента**: когда вызывать, когда нет, что вернёт (≤ 1000). От этого текста зависит, найдёт ли агент ручку |
| `path` | да | путь на служебном порту; параметры пути — `{name}`. Рекомендуемый префикс — `/diag/` |
| `params` | нет | параметры: в пути (`{name}`) или в query |
| `timeout_ms` | нет | сколько ждать ответа, по умолчанию 5000, не больше 10000 |
| `response` | да | **схема ответа** — всё, что pulse пропустит к агенту |
| `rows_path` | нет | если ответ — список, где он лежит (`"items"`), чтобы pulse мог ограничить число строк |
| `max_rows` | нет | сколько строк списка показать агенту, по умолчанию 50, не больше 100 |

### Параметры

```json
"params": {
  "number": { "type": "string", "pattern": "[0-9]{5,12}", "description": "номер заказа" },
  "limit":  { "type": "integer", "min": 1, "max": 100, "default": 20 },
  "state":  { "type": "string", "enum": ["pending", "failed"] },
  "phone":  { "type": "string", "x-personal": "phone", "description": "телефон клиента" }
}
```

- Типы: `string`, `integer`, `number`, `boolean`.
- `pattern` — регэксп в синтаксисе RE2 (его проверяет pulse): без lookahead и обратных ссылок.
  **Проверяется всё значение целиком**: pulse (и pulsekit) сам окружает шаблон якорями
  `^(?:…)$`, поэтому `[0-9]{5,12}` не пропустит `234115; drop`. Писать `^…$` не нужно — но и не
  мешает.
- **Строковый параметр обязан иметь `pattern`, `enum` или `x-personal`.** Свободная строка —
  отказ ручке: иначе ручку можно превратить в поиск по чему угодно.
- **Персональный параметр** (`x-personal` с видом, см. «Персональные данные — токенами»)
  модель передаёт **токеном** (`pii:phone:jlcodpanlkmi`); настоящее значение подставляет
  pulse_agent, pulse приводит его к одному виду (телефон — цифры с кодом страны) и проверяет
  формат по виду, `pattern` не нужен. Так делаются ручки для расследований вроде «заказы
  клиента по телефону» — при условии, что персональные поля ответа помечены `x-personal`.
- Остальные строковые параметры — технические идентификаторы (номер заказа, id задачи, код
  склада). Поиск по ФИО не делайте: имя не нормализуется, и такой поиск — выгрузка людей.
- Неизвестный параметр, неверный тип, выход за `min`/`max` — pulse отказывает сам, до запроса
  к сервису.

### Схема ответа

Подмножество JSON Schema — ровно то, что нужно, чтобы pulse мог «спроецировать» ответ на
схему:

- `type`: `object`, `array`, `string`, `integer`, `number`, `boolean`;
- `properties` у объектов, `items` у массивов;
- `enum`, `format: "date-time"`, `maxLength` (у строк), `maxItems` (у массивов), `description`;
  `enum` — подсказка модели, какие значения бывают: значение не из перечня (1С прислала новый
  `task_type`) pulse **не вырезает**, оно доходит как есть;
- `additionalProperties` — только для словарей с **числовыми или булевыми** значениями
  (`{"new": 12, "paid": 40}`); ключи словаря — как обычный текст;
- расширение **`x-personal: "<вид>"`** — поле с персональными данными: сервис сам говорит, что
  в нём лежит, а модель видит вместо значения токен (см. «Персональные данные — токенами»).

`$ref`, `oneOf`/`anyOf`, `patternProperties` не поддерживаются: схема должна однозначно
говорить, какие поля есть.

## Конфиденциальность

Всё, что возвращает pulse, уходит **за периметр компании**: в LLM-провайдера (OpenAI) и в
чаты, где задают вопросы, и хранится в журнале вопросов 90 дней. Поэтому вопрос для каждого
поля — не «секрет ли это», а **«можно ли это вынести наружу»**.

### Правило одной фразой

> **В диагностику — только то, что вы бы показали на общем дашборде в Grafana всем
> инженерам.**

Состояние системы и агрегаты — да. Выгрузки записей о людях — нет. Один объект по его номеру
(заказ, задача, платёж — без данных о человеке) — да. Списки клиентов — нет.

### Как защищает стандарт

Обычный подход «найти и замаскировать» (список опасных полей, регэкспы) дырявый по
построению: забыли поле — оно утекло. Стандарт устроен наоборот — **пропускается только
объявленное**, и защита стоит в двух местах.

**1. pulse проецирует ответ на схему.** Из ответа ручки к агенту доходят только поля,
описанные в `response`. Всё остальное вырезается, даже если сервис его вернул.
Разработчик добавил в структуру ответа `customer_phone` и забыл про безопасность — поле не
уйдёт, пока его явно не впишут в схему. А правка схемы видна на ревью как отдельная строка.

Сколько полей вырезано, pulse показывает в каталоге (`get_service_info`) — владелец видит,
что ручка отдаёт лишнее, и может убрать это у себя.

**2. Модель видит персональные данные только токенами.** Поле с `x-personal` pulse отдаёт с
отметкой вида (`personal_fields`), и pulse_agent заменяет значение токеном до модели. По
токену модель ведёт расследование дальше (ищет в логах, спрашивает другой сервис), не узнавая
самих данных. Подробно — ниже.

**3. Секреты объявлять нельзя.** Поле, имя которого похоже на секрет (`password`, `passwd`,
`secret`, `token`, `api_key`, `private_key`, `credential`, `dsn`, `cookie`, `session`,
`authorization`, `signature`…), pulse не принимает: ручка отклоняется, в каталоге — причина.
Исключений нет — если поле не секрет, переименуйте его.

**4. Свободный текст — под подозрением.** Во всех строковых полях pulse маскирует номера карт и
вырезает `логин:пароль@` из адресов, а pulse_agent находит телефоны и email и заменяет их
токенами (как у `x-personal`). Строки длиннее `maxLength` (по умолчанию 500) обрезаются. Но это
страховка — см. «Чего не отдавать».

**5. Параметры — только технические идентификаторы** с `pattern`/`enum` (см. «Параметры»).

**6. Ручки недоступны снаружи**: служебный порт не публикуется в ruto/ingress (или пути
закрыты на ingress, если порт один); только `GET`.

**7. Аудит.** Каждый вызов записан в журнал вопросов агента: кто спросил, какую ручку,
с какими параметрами и что вернулось (как это видела модель — токенами, персональных данных
в журнале нет). У сервиса —
`X-Pulse-Request-Id` в логе. По любому вызову можно восстановить, кто и зачем смотрел
данные.

**8. Защита у источника.** Схема строится из тех же типов, которые сериализуют ответ, —
тогда схема и ответ не расходятся, и необъявленное поле сервис не отдаст вовсе. Модуль
gotemplate делает это из Go-структуры; в других стеках то же дают pydantic (Python), zod
(TypeScript), OpenAPI-генераторы. Персональные поля сервис отдаёт **как есть** — токенизирует
их pulse_agent: для токена нужен ключ, и раздавать его сервисам нельзя. Граница — модель:
к LLM-провайдеру и в журнал значения не уходят.

Итог: утечка требует **двух** ошибок сразу — у разработчика (явно объявил в схеме поле с
чувствительными данными без пометки) и на ревью (не заметил эту строку). Ни одно звено не
зависит от того, угадали ли мы регэксп.

### Персональные данные — токенами

Расследование часто идёт по человеку: «у клиента не проходят заказы» → его заказы в одном
сервисе → по телефону в логах → в другом сервисе. Если персональные данные просто
замаскировать (`***`), цепочка рвётся. Поэтому модель видит их **токенами**:

```
"customer_phone": "+7 701 123 45 67"   →   "customer_phone": "pii:phone:jlcodpanlkmi"
```

**Кто это делает.** Токены — забота только **pulse_agent**, того, кто передаёт данные модели.
Сервис отдаёт значения как есть и помечает их `x-personal`; pulse проецирует ответ и передаёт
отметки дальше (`personal_fields`: путь → вид); pulse_agent на своей границе с моделью:

- заменяет токенами телефоны и email в вопросе человека, в истории беседы и во всех ответах
  pulse, а поля из `personal_fields` — по их виду;
- токен в запросе модели к pulse (`query_logs`, параметр ручки) заменяет настоящим значением —
  pulse получает обычный номер и ищет его в любом написании;
- в готовом ответе заменяет токены обратно: человек в Telegram (и любая другая система-клиент)
  получает настоящий номер и не знает, что внутри были токены.

- **Формат**: `pii:<вид>:<12 букв a–p>`. Буквы, а не цифры: токен нельзя принять за телефон или
  номер карты при повторной обработке текста.
- **Токен постоянный.** Он вычисляется из значения (HMAC с секретным ключом pulse_agent), поэтому
  один и тот же телефон даёт один и тот же токен — в ответе сервиса, в строках логов, в разных
  вопросах. Модель видит «один клиент в трёх заказах», не зная, кто это. Без ключа токен не
  обратить, даже перебором номеров.
- **Сами данные** не попадают ни к LLM-провайдеру, ни в журнал вопросов: там только токены.

**Виды персональных данных** (`x-personal: "<вид>"`). Вид сервис указывает сам — от него
зависит, как значение приводится к одному виду перед токеном (иначе `+7 701…`, `8701…` и
`7701…` дали бы разные токены) и можно ли подставить его обратно:

| Вид | Что это | Приведение к одному виду | Поиск по токену |
|---|---|---|---|
| `phone` | телефон | только цифры, код страны (`8…` → `7…`) | да |
| `email` | почта | нижний регистр, без пробелов | да |
| `iin` | ИИН / ИНН / БИН | только цифры | да |
| `customer_id` | внутренний id клиента, если по нему можно установить личность | как есть | да |
| `name` | ФИО | нижний регистр, одинарные пробелы | нет — имя не уникально |
| `address` | адрес | — | нет |
| `document` | паспорт, удостоверение | — | нет |
| `card` | номер карты | — | **нет, и токен не выдаётся**: pulse всегда отдаёт `***` + последние 4 цифры |
| `other` | прочее личное | как есть | нет |

Тонкости:

- **В ответе человеку раскрывается любой вид**, который pulse_agent видел за последние сутки.
  В запросы к pulse — только виды с поиском (телефон, email, ИИН, id клиента): токен имени или
  адреса модель в поиск не передаст.
- **Имена в свободном тексте** надёжно не распознать — они становятся токенами, только если
  пришли полем с `x-personal: "name"`. Поэтому тексты от пользователей по-прежнему не отдаются.
- **Прямые клиенты pulse** (разработчик через MCP) видят данные как есть: карты и пароли
  вырезаны, телефоны и email — нет. pulse — инструмент диагностики внутри компании; прятать
  данные от модели — задача того, кто её вызывает.
- **Ключ токенов** живёт в конфигурации pulse_agent (секрет) и меняется редко: после смены
  старые токены в журнале перестают совпадать с новыми.

### Чего не отдавать никогда

| Нельзя | Почему | Что вместо |
|---|---|---|
| пароли, токены, ключи, строки подключения | секреты | факт: «ключ задан», «подключение ok» |
| ФИО, телефоны, email, адреса, ИИН, паспорта, карты — **без пометки** | персональные данные | `x-personal` с видом — модель получит токен; или факт наличия: `has_phone: true` |
| тексты от пользователей: комментарии к заказу, отзывы, сообщения в чат | персональные данные **и** возможность подложить агенту инструкции («игнорируй правила и…») | категория/длина: `comment_present: true` |
| сырые ответы внешних систем, SQL, тела запросов | в них оказывается всё перечисленное | код ответа, короткая причина своими словами |
| текст исключения как есть (`err.Error()`, `str(e)`, `e.message`) | драйверы кладут туда DSN и данные | своё сообщение |
| выгрузки: «все заказы клиента», «последние 1000 платежей» | это уже база данных, а не диагностика | агрегаты: количества, статусы, время |

### Проверка перед мержем (для ревьюера)

- [ ] Каждое поле в `response` можно показать на общем дашборде.
- [ ] Персональные поля и параметры помечены `x-personal` с правильным видом — или убраны, если для расследований не нужны.
- [ ] Строковые параметры — с `pattern` или `enum`, и это технические идентификаторы.
- [ ] В `message` и текстах ошибок — свои формулировки, не текст исключения как есть.
- [ ] Ручки на служебном порту; если на основном — пути закрыты на ingress и не опубликованы в ruto.
- [ ] Нет текстов от пользователей.
- [ ] Ручка ничего не меняет, отвечает быстро и не делает тяжёлых запросов (есть индекс, есть `LIMIT`).

## Что делает pulse с ответом — по шагам

Для понимания, что увидит агент:

1. Проверяет параметры по описанию (тип, `pattern`/`enum`/вид персональных данных, границы).
   Не прошли — отказ без запроса к сервису. Персональный параметр приводит к одному виду
   (токен в настоящее значение до этого заменил pulse_agent).
2. Вызывает ручку на готовом поде: `GET`, таймаут из манифеста (≤ 10 с), тело ≤ 256 KB.
3. Не-JSON, редирект, превышение размера — ошибка «ручка ответила не по стандарту».
4. **Проецирует** ответ на схему `response`: необъявленные поля вырезаются, типы сверяются
   (не совпал — поле вырезается), массивы режутся по `maxItems`/`max_rows`.
5. Маскирует карты и `логин:пароль@`; обрезает строки по `maxLength`.
6. Отдаёт данные и служебные поля: `truncated`, `rows`/`total_rows`, `personal_fields`
   (путь → вид персонального поля), `dropped_fields` (сколько вырезано), `request_id` (тот же
   `X-Pulse-Request-Id`, что ушёл сервису). Ответ с ошибкой — только текст `error`, остальное
   тело не пропускается; не JSON — ошибка «ручка ответила не по стандарту».
7. pulse_agent заменяет токенами поля из `personal_fields`, телефоны и email в любом тексте и
   передаёт ответ модели; вызов пишется в журнал вопросов агента.

## Go: модуль в gotemplate

**Эталон пакета — gotemplate** (`internal/infra/pulsekit`): в сервис он копируется целиком, со
всеми тестами, и на месте не правится — замечания и правки идут в шаблон. **Образец** подключения
(ручка, зависимости, пассивная проверка, показатель, тест ручки) — `internal/infra/pulsekit/example_test.go`:
это работающие тесты, скопируйте и переименуйте под свой домен. Тест манифеста самого сервиса —
`internal/app/manifest_test.go` в шаблоне; к нему добавьте `kit.CheckEndpoint` для каждой ручки. Сервисы, созданные из
gotemplate, получают всё готовым: пакет `internal/infra/pulsekit` отдаёт
манифест, ручку состояния и диагностические ручки; при генерации cookiecutter спрашивает название,
описание, команду и критичность (`internal/app/manifest.go`), Postgres уже объявлен зависимостью,
полный коммит сборки передаётся через ldflags. Старому сервису на gotemplate — перенести пакет
`internal/infra/pulsekit` и `internal/app/manifest.go` из шаблона и подключить, как ниже.

**Зависимости** сервис объявляет сам — одной строкой рядом с созданием клиента в `app.go`:

```go
// pg
a.pgpool, err = initPgPool(config.Conf.PgDsn)
errCheck(err, "pgpool init")
a.pulsekit.Depend("pg", "postgres", pulsekit.Host(config.Conf.PgDsn), true, a.pgpool.Ping).
	Affects("приём и выдача заказов")

// 1С — своя проверка функцией
a.pulsekit.Depend("onec", "http", pulsekit.Host(config.Conf.OnecUrl), false, func(ctx context.Context) error {
	return onecClient.Ping(ctx)
}).Affects("выгрузка заказов в 1С")

// банк — платный API без health-ручки: пассивная проверка по настоящим вызовам
bank := pulsekit.NewPassive(5 * time.Minute)
a.pulsekit.Depend("bank", "http", pulsekit.Host(config.Conf.BankUrl), false, bank.Check).Affects("онлайн-оплата")
// в клиенте банка после каждого вызова:
rep, err := bankApi.Pay(ctx, req)
bank.Observe(err)
```

Аргументы: `id`, вид (`postgres`, `redis`, `kafka`, `http`…), `target` — хост без учётных данных,
`critical`, проверка «работает ли» (Ping клиента). Адрес из конфигурации — только через
`pulsekit.Host`: она понимает URL (`postgres://user:pass@db:5432/app`), DSN вида
`host=db port=5432 password=…`, gRPC (`dns:///orders:9090`) и `host:port` и возвращает только хост;
не распознала — пусто. target с учётными данными или похожий на строку подключения в манифест
не попадает: вместо него — `unknown` и предупреждение в лог (адрес приходит из окружения — ронять
сервис из-за него нельзя). Проверки идут в фоне раз в 30 с; в ручке состояния — своё короткое
сообщение («таймаут», «в соединении отказано»), а не текст ошибки. Тот же классификатор —
`pulsekit.Describe(err)` — годится для своих сообщений: различает сеть (таймаут, отказ в
соединении, хост не найден, не отвечает), авторизацию и ответы системы (не найдено, отклонено,
внутренняя ошибка), иначе — «ошибка»; для сохранённых текстов (причина застревания в БД) —
`pulsekit.DescribeText(text)`. Своя проверка может вернуть `pulsekit.Problem{Status, Message}` —
свой статус (`ok` с пометкой, `degraded`, `down`) и своё сообщение.

**Показатели состояния** (`gauges`) — то, чего нет в метриках и что объясняет состояние. Читаются
в фоне вместе с проверками; статус не `ok` делает сервис `degraded`:

```go
a.pulsekit.Gauge("outbox_backlog", "Неотправленные события", "count", func(ctx context.Context) (float64, string, error) {
	n, err := outboxRepo.Count(ctx)
	return float64(n), lo.Ternary(n > 1000, "degraded", "ok"), err
})
a.pulsekit.GaugeTime("last_1c_sync", "Последняя выгрузка в 1С", func(ctx context.Context) (time.Time, string, error) {
	return syncService.LastSuccess(ctx)
})
```

**Метрики, ошибки в логах, инструкции**: `a.pulsekit.Metric(pulsekit.Metric{Id, Title, PromQL,
Unit, Direction})`, `a.pulsekit.ErrorPattern("1С недоступна", "onec: .*timeout")`, инструкции для
дежурных — `Runbooks` в `pulsekit.Service` (`internal/app/manifest.go`).

**Отчёт по объектам** в ручке состояния — `a.pulsekit.Activity("заказ", degradedAtStuck, read)`:
`read` получает пороги `StuckAfter` из `Domain` и возвращает счётчики по статусам (один запрос с
`GROUP BY status`); вызывается в фоне, не на каждый запрос pulse. Образец — `ExampleKit_Activity`.

**Бизнес-смысл** — `Domain` в `pulsekit.Service` (`internal/app/manifest.go`): `Responsibilities`,
`NotResponsible`, `Entities` (с `IdPattern`, `IdExample`, `Statuses` и `StuckAfter`), `Questions`.
Имена статусов — из констант кода (`string(OrderPaid)`), чтобы не разъехались. Образец —
`ExampleDomain`; неверный формат номера или вопрос со ссылкой на необъявленную ручку — в
`kit.Problems()`.

**Диагностическая ручка** — функция с типизированным ответом, схема строится из типа:

```go
type orderStatusRep struct {
	Number    string       `json:"number"`
	Status    string       `json:"status" pulse:"enum=new|paid|shipped,description=статус: new — создан, paid — оплачен"`
	Phone     string       `json:"customer_phone" pulse:"personal=phone"`
	Reason    string       `json:"stuck_reason" pulse:"maxLength=300"`
	ShippedAt *time.Time   `json:"shipped_at"` // nil — null: ещё не отгружен
	History   []historyRep `json:"history" pulse:"maxItems=50"`
}

pulsekit.Handle(a.pulsekit, pulsekit.Endpoint{
	Id:          "order_status",
	Title:       "Где заказ в конвейере",
	Description: "Вызывай, когда спрашивают о конкретном заказе по номеру…",
	Path:        "/diag/order/{number}",
	Params: map[string]pulsekit.Param{
		"number": {Pattern: "[0-9]{5,12}"},
		"limit":  {Type: "integer", Default: "20"}, // в манифесте — числом 20
	},
}, func(ctx context.Context, params map[string]string) (orderStatusRep, error) {
	order, err := ordersUsecase.Status(ctx, params["number"])
	if errors.Is(err, errs.ObjectNotFound) {
		return orderStatusRep{}, pulsekit.Error{Status: http.StatusNotFound, Message: "заказ не найден"}
	}
	…
})
```

- Тег `pulse:"…"`: `personal=<вид>`, `maxLength=`, `maxItems=`, `enum=a|b|c`, `description=` —
  **последним**: берётся всё до конца тега, запятые можно.
- Перечень значений без дублирования констант: у строкового типа поля метод
  `PulseEnum() []string` — enum берётся из него (`type ReasonCode string` + список кодов рядом с
  константами).
- Персональное поле — `personal=<вид>`; значение отдаётся как есть, токеном его заменит
  pulse_agent (ключ токенов есть только у него).
- Время — `time.Time` (RFC 3339 со смещением, UTC — `Z`); указатель `nil` — `null`.
- Каждый вызов pulsekit пишет в лог сам: ручка, `X-Pulse-Request-Id`, параметры (персональные —
  только вид), статус, время. Для своих строк лога — `pulsekit.RequestId(ctx)`.
- **Манифест никогда не роняет сервис.** Нарушение стандарта при объявлении (строковый параметр
  без `Pattern`/`Enum`/`Personal`, поле или параметр с именем секрета, словарь не с числами,
  `Default` не в типе параметра, неизвестный вид персональных данных) pulsekit пишет в лог и в
  `kit.Problems()`, а неправильный элемент не публикует — остальной манифест работает. Тексты
  длиннее лимитов — только предупреждение (`kit.Warnings()`). Строгость — в тестах: тест манифеста
  требует пустой `Problems()`, а `CheckEndpoint` неопубликованной ручки возвращает ошибку.
- Ошибка для человека — `pulsekit.Error{Status, Message}`; любая другая ошибка уходит как
  «внутренняя ошибка»: её текст наружу не попадает, в лог сервиса — попадает.
- **Проверка ответа в тесте** — `kit.CheckEndpoint(id, params)`: вызывает ручку, как pulse, и
  сверяет ответ со схемой (лишние поля, типы, `maxLength`, `maxItems`, `enum`, время; у ошибки —
  только `{"error"}`). Зависимости ручки в тесте — фейки:

```go
func TestOrderStatusEndpoint(t *testing.T) {
	kit := pulsekit.New(pulsekit.Config{}, testService, pulsekit.Build{})
	handleOrderStatus(kit, fakeOrders{})
	require.NoError(t, kit.CheckEndpoint("order_status", map[string]string{"number": "234115"}))
	require.NoError(t, kit.CheckEndpoint("order_status", map[string]string{"number": "00000"})) // 404 по стандарту
}
```

## Частые вопросы

Собраны из пилота (caravan). Если ответа нет — спроси разработчика и предложи добавить вопрос сюда.

**Персональные данные и ответы**

- *Увижу ли я настоящий номер клиента в ответе агента?* Да. Модель видит токен (`pii:phone:…`) и
  ищет по нему дальше, человек в итоговом ответе получает настоящее значение. Поля вроде
  `phone_last4` не нужны — помечайте `x-personal`.
- *Значение не из `enum` (1С прислала новый тип)?* pulse его не вырезает — `enum` только подсказка
  модели. Перечень из кода без дублирования — метод `PulseEnum()` у типа поля (Go).
- *Время в UTC (`…Z`) — можно?* Да, это тоже смещение по RFC 3339. `null` — «нет значения».
- *Описание обрезается или длинное?* Лимиты мягкие: название ≤ 100, описание ≤ 500, описание
  ручки ≤ 1000 — длиннее pulse обрежет и покажет причину в каталоге, pulsekit предупредит
  (`kit.Warnings()`). В теге pulsekit `description=` — последним, запятые можно.
- *Может ли ошибка в манифесте уронить сервис?* Нет: сервис не ходит в pulse, а pulsekit при
  нарушении стандарта только не публикует неправильный элемент и пишет причину в лог и в
  `kit.Problems()`.
- *`pattern` — с `^…$` или без?* Без: значение всегда проверяется целиком.

**Зависимости**

- *`critical` или нет, если без зависимости ломается только выдача?* `critical` — «весь сервис
  лежит»; что именно ломается — в `affects` («выдача заказов»).
- *Интеграция настроена не во всех окружениях?* Объявляйте только настроенную: разный состав
  зависимостей у одного образа — нормально.
- *`target` с портом?* Нет — только имя (`orders-pg`, `api.bank.kz`). Адрес из конфигурации — через
  `pulsekit.Host`: она отрежет схему, учётные данные, порт и параметры.
- *Как проверять платный API, API с лимитами, без health-ручки?* Пассивной проверкой по
  настоящим вызовам (`pulsekit.NewPassive`).
- *Что считать сбоем в пассивной проверке — любой 4xx?* Нет, смысл такой: сбой — зависимость не
  сделала свою работу для сервиса. 404 геокодера на плохой адрес — штатный ответ, не сбой; 401,
  429 или 400 от OpenAI — поломка интеграции (ключ, квота, неправильные запросы), сбой. Решает
  сервис.
- *А если критичный API вызывается редко (оплата — только при выдаче)?* Пассивная + TCP: вызовы
  были — судит пассивная, не было (`Passive.Idle()`) — TCP и `ok` с пометкой «вызовов не было, сеть
  до хоста есть». Своё время последнего вызова хранить не нужно.
- *gRPC health через общее соединение портит метрики клиента?* Проверяйте через отдельное
  соединение без перехватчиков или по состоянию соединения (`READY`).
- *Какое сообщение писать при сбое?* Своё короткое, не текст ошибки: `pulsekit.Describe(err)` /
  `DescribeText(text)` — таймаут, отказ в соединении, не найдено, отклонено, внутренняя ошибка.
- *Пороги показателей (`gauges`): 30 минут — это много?* Решает владелец сервиса — агент
  предлагает, человек подтверждает.
- *Что писать в отчёт по объектам (`entities` ручки состояния)?* Объекты из `domain` со статусами,
  которые меняются (незавершённые): сколько в каждом и сколько застряло дольше `stuck_after`.
  Завершённые (доставлено, отменено) не нужны — только поток за час, если он есть. Считать — одним
  запросом с группировкой по статусу, в фоне; `degraded` — когда застрявших столько, что это уже
  проблема (решает владелец).
- *Зачем `domain`, если есть описание?* Описание говорит, что сервис делает; `domain` — как читать
  его данные: чей номер, что значит статус, когда объект застрял, где искать причину, если сервис
  ни при чём. Черновик агент собирает из кода, `stuck_after` и границы подтверждает человек.

**Порт, сервис, метрики**

- *Какой порт найдёт pulse?* Тот, где `/metrics`, или порт с именем `system`/`http*` у контейнера
  либо у k8s Service; иначе — аннотация пода `pulse/port`.
- *В чарте есть фронт, другой продукт и Postgres — они часть сервиса?* Нет: сервис — образы
  одного репозитория. Остальное — отдельные сервисы.
- *У метрик префикс из переменной окружения — как его подставить в PromQL?* Сервис строит манифест
  при запуске — подставьте префикс сами, плейсхолдер не нужен.
- *«Не найдено», «неверный код» считаются ошибками и дают error_rate — скрывать их?* Нет: цифры
  нужны. Отличайте их лейблом `code` в метрике запросов (в gotemplate — `errs.Err` → `code`):
  pulse покажет сбои в `error_rate`, а отказы по делу — отдельно в `rejected_rate`. Отказ пишите в
  лог уровнем info, сбой — error.

**Реализация (Go)**

- *Какая копия pulsekit главная?* gotemplate (`internal/infra/pulsekit`): копируется в сервис
  целиком, со всеми тестами, и на месте не правится.
- *Как писать ручку и её тест?* Образец — `internal/infra/pulsekit/example_test.go`: ручка,
  зависимости, пассивная проверка, `kit.CheckEndpoint` в тесте.
- *Нужно ли писать `X-Pulse-Request-Id` в лог?* pulsekit пишет каждый вызов сам; для своих строк —
  `pulsekit.RequestId(ctx)`.
- *Сколько вопросов задавать разработчику?* Не больше 4 за раз, по важности — см. «Для агента».

## Настройки pulse (для администратора)

Секция `manifest` в правилах pulse (`conf.yml`):

| Параметр | По умолчанию | Описание |
|---|---|---|
| `path` | `/.well-known/pulse` | путь манифеста (ручка состояния — `<path>/status`) |
| `default_ports` | `[3003]` | порты, если нет аннотации и портов с именами `system`/`http` |
| `annotation_prefix` | `pulse/` | префикс аннотаций пода (`pulse/port`, `pulse/path`) |
| `refresh_after` | `24h` | как часто перечитывать манифест без выкатки |
| `retry_after` | `1h` | повтор после неудачи |
| `status_cache` | `15s` | сколько кэшировать ответ состояния |
| `phone_country_code` | `7` | код страны для телефонов в параметрах ручек и поиске в логах (`8…` → `7…`) |

Ключ токенов персональных данных — секрет в окружении pulse_agent (`PII_TOKEN_KEY`), у pulse его нет.
