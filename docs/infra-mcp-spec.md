# ТЗ: центральный MCP-сервис инфраструктурного контекста (`infra-mcp`)

Документ предназначен для агента-исполнителя, который будет реализовывать сервис.
Читать целиком перед началом работы над любой фазой.

---

## 0. Контекст

### 0.1. Что строим

Один Go-сервис, реализующий MCP-сервер. Единственная точка, через которую LLM-агент
получает информацию об инфраструктуре и сервисах компании. Агент не ходит напрямую
ни в Kubernetes, ни в Prometheus, ни в Loki, ни в GitHub — только в `infra-mcp`.

Конечная цель: чат-бот, отвечающий на вопросы вида «что пошло не так?», «какая
ситуация по системе X?», «почему не проходят платежи?».

### 0.2. Существующий ландшафт

| Компонент | Состояние |
|---|---|
| Kubernetes | есть, продовый кластер |
| Prometheus | есть, метрики сервисов |
| Loki | логи |
| kusec | своя база configmaps и secrets, **есть готовый MCP** и API |
| GitHub | много репозиториев: Go-сервисы и фронтенды |
| ruto | API-gateway, отдаёт метрики и список опубликованных ручек |
| Манифесты | в **отдельном** репозитории, не в репах сервисов |

Заказчик предоставит в начале реализации: проект репозитория манифестов и проект
kusec. До этого момента интеграции с ними описываются в спеке через интерфейсы,
реализация — после получения структуры.

### 0.3. Ключевые архитектурные решения (не пересматривать без согласования)

**Р1. Fan-out вместо тонких ручек.** Основная ценность сервиса — параллельный сбор
из нескольких источников за один вызов инструмента. Агент делает 1 tool call вместо
15 последовательных. Проектировать инструменты от вопросов пользователя, а не от
структуры источников данных.

**Р2. Join key — имя образа.** Связка «под в кластере → репозиторий на GitHub →
метаданные сервиса» строится через имя и тег container image, а не через labels в
манифестах и не через ручку в самом сервисе. Манифесты лежат в отдельной репе и не
должны редактироваться ради этого сервиса.

**Р3. Метаданные — файл `service.yaml` в корне репозитория сервиса.** Не ручка в
сервисе: метаданные нужнее всего тогда, когда сервис лежит и его ручки недоступны;
плюс фоновые джобы вообще не имеют портов.

**Р4. Состояние всегда запрашивается живьём, в индексе хранится только топология.**
В БД сервиса не должно быть значений метрик, содержимого логов, текущих счётчиков.
Индекс хранит связи (сервис ↔ namespace ↔ deployment ↔ репозиторий ↔ команда) и
метаданные. Всё остальное — real-time запрос в источник.

**Р5. Read-only.** Сервис не выполняет никаких мутирующих операций ни в одном из
источников. Никогда.

**Р6. Метрики отдаются в сравнении с базовой линией.** Абсолютное значение бесполезно
для LLM. Всегда: текущее / час назад / вчера в это же время + дельта в процентах.

**Р7. Секреты не покидают сервис.** Значения секретов не попадают в ответ инструмента
ни при каких условиях. Подробности — раздел 4.2.

### 0.4. Технологический стек

- Go (версия по договорённости, минимум 1.22)
- MCP: официальный Go SDK (`github.com/modelcontextprotocol/go-sdk`), транспорт
  streamable HTTP
- Хранилище индекса: PostgreSQL
- Kubernetes: `client-go`, in-cluster конфиг, отдельный ServiceAccount, RBAC
  строго `get/list/watch`
- Prometheus / Loki: HTTP API напрямую
- GitHub: REST API v3 через официальный клиент

### 0.5. Терминология

- **Сервис (service)** — логическая единица: один репозиторий на GitHub, один или
  несколько workload'ов в кластере.
- **Workload** — Deployment / StatefulSet / DaemonSet / CronJob в k8s.
- **Снапшот (snapshot)** — агрегированный срез состояния сервиса на текущий момент.
- **Окно (window)** — временной интервал запроса, формат Go duration (`15m`, `2h`, `24h`).

## 1. Общие требования ко всем фазам

### 1.1. Формат ответов инструментов

Все инструменты возвращают JSON. Требования:

- Ответ должен быть самодостаточным для LLM: не отдавать сырые k8s-объекты и не
  отдавать идентификаторы без человекочитаемых имён.
- Ограничение размера: любой ответ ≤ 100 KB. Если данных больше — усечение с полем
  `truncated: true` и `total_count`.
- Все временные метки — RFC3339 UTC.
- Ошибка источника не роняет весь ответ. Если Loki недоступен, а Prometheus жив —
  вернуть данные Prometheus и поле `errors: [{source: "loki", message: "..."}]`.
  Это критично: агент должен понимать, что часть картины отсутствует, а не получать
  пустоту.

### 1.2. Нормализованное событие

Единый тип для всего, что имеет время. Используется в таймлайне (фаза 4) и в
снапшоте. Ввести на фазе 2, придерживаться до конца.

```go
type Event struct {
    TS       time.Time         `json:"ts"`
    Source   string            `json:"source"`   // k8s | prometheus | github | kusec | alertmanager | ruto
    Type     string            `json:"type"`     // deploy | restart | oom_kill | alert_firing | config_change | commit | scale
    Service  string            `json:"service"`
    Severity string            `json:"severity"` // info | warning | critical
    Summary  string            `json:"summary"`  // одна строка на человеческом языке
    Details  map[string]any    `json:"details,omitempty"`
}
```

`Summary` пишется так, чтобы его можно было показать человеку без обработки:
`"payments-api: деплой a3f9c21 → b7e1d02, автор i.petrov"`.

### 1.3. Общая конвенция параметров

- `service` — имя сервиса из каталога. Если передано неизвестное имя, инструмент
  возвращает ошибку со списком похожих имён (fuzzy), а не пустой результат.
- `window` — Go duration, по умолчанию `1h`, максимум `7d`.
- Все инструменты, принимающие `service`, должны также принимать массив сервисов
  там, где это осмысленно.

### 1.4. Описания инструментов

Описание каждого инструмента (`description` в MCP) — часть продукта, а не
комментарий. Требования:

- Указывать, **когда** инструмент выбирать и когда не выбирать.
- Указывать, что именно возвращается, в одном предложении.
- Не превышать 4–5 строк: описания всех инструментов конкурируют за контекст модели.

Общее количество инструментов на всех фазах — **не более 12**. Если появляется
потребность в тринадцатом, сначала объединять существующие.

## Фаза 0. Скелет

**Цель:** работающий MCP-сервер без предметной логики.

### Объём

1. Структура проекта, конфигурация (env + yaml), структурное логирование
   (`log/slog`, JSON handler).
2. MCP-сервер на streamable HTTP, регистрация инструментов, graceful shutdown.
3. Подключение к PostgreSQL, миграции (любой стандартный инструмент).
4. Health/readiness эндпоинты.
5. Один тестовый инструмент `ping`, возвращающий версию сервиса и статус
   подключений к источникам.

### Критерии приёмки

- MCP-клиент подключается, видит список инструментов, вызывает `ping`.
- Сервис стартует при недоступности любого внешнего источника, отражая это в `ping`.

## Фаза 1. Каталог и резолвинг (ядро)

**Цель:** сервис знает, какие сервисы существуют, где они живут и как называются на
человеческом языке.

Это фундамент. Пока фаза 1 не работает надёжно, остальные фазы бессмысленны:
все они принимают на вход имя сервиса.

### 1.1. Индексер топологии

Фоновый воркер, периодический обход (интервал конфигурируемый, старт — 5 минут):

1. Обойти namespace'ы кластера (список исключений — в конфиге).
2. Собрать workloads: Deployment, StatefulSet, DaemonSet, CronJob.
3. Для каждого workload собрать поды и извлечь `image` из спеки контейнеров.
4. Распарсить образ: `registry.host/path/name:tag` → имя репозитория и тег.
   Правила маппинга «имя образа → GitHub-репозиторий» вынести в конфиг, поскольку
   они специфичны для конкретного registry:

   ```yaml
   image_mapping:
     - registry: registry.company.kz
       repo_template: "github.com/{org}/{image_name}"
       org: org
   ```

5. Если тег выглядит как SHA коммита — сохранить как `deployed_commit`. Это даёт
   бесплатный ответ на «какая версия сейчас в проде» и используется в фазе 4.

### 1.2. Метаданные: `service.yaml`

Файл в корне репозитория сервиса. Читается индексером через GitHub API из ветки по
умолчанию. Отсутствие файла — не ошибка: сервис попадает в каталог с данными,
выведенными из кластера, и флагом `metadata: false`.

Схема (все поля кроме `name` опциональны):

```yaml
name: payments-api
title: Приём платежей
aliases: [платежи, оплата, эквайринг, payments]
owner:
  team: team-billing
  contacts: ["@i.petrov", "billing@company.kz"]
criticality: high        # high | medium | low
description: >
  Принимает платежи от фронта, ходит в эквайринг, пишет в billing-core.

metrics:                 # семантика метрик — то, чего не даёт discovery
  - id: success_rate
    title: Доля успешных платежей
    promql: 'sum(rate(payments_completed_total[5m])) / sum(rate(payments_started_total[5m]))'
    unit: ratio
    direction: higher_is_better
  - id: acquirer_latency
    title: Задержка эквайринга p95
    promql: 'histogram_quantile(0.95, sum by (le) (rate(acquirer_request_duration_seconds_bucket[5m])))'
    unit: seconds
    direction: lower_is_better

logs:
  selector: '{app="payments-api"}'
  error_patterns:        # опционально, для фазы 3
    - name: acquirer_timeout
      pattern: "acquirer.*timeout"

runbooks:
  - title: Платежи не проходят
    url: https://...

endpoints: []            # заполняется на фазе 6
```

**Важно:** этот файл содержит только то, что не выводится автоматически — алиасы,
семантику метрик, владельца, критичность. Не дублировать сюда namespace, реплики,
env, порты. Всё это берётся живьём.

### 1.3. Модель данных

```sql
services (
  name, title, repo_url, description, criticality,
  owner_team, owner_contacts, aliases[],
  metadata_present, metadata_raw jsonb,
  first_seen, last_seen
)

workloads (
  service_name, cluster, namespace, kind, name,
  replicas_desired, image, deployed_commit, last_seen
)
```

Каталог полностью производный. Ручного редактирования не предусмотрено: любая
правка делается в `service.yaml` и приезжает следующим циклом индексации.

### 1.4. Инструменты

**`resolve_service(query: string) -> Candidate[]`**

Переводит человеческую формулировку в имена сервисов. Внутри — обычный код, не LLM:
точное совпадение имени → совпадение по алиасам → fuzzy по имени и title →
подстрока в description.

```json
[
  { "service": "payments-api", "title": "Приём платежей",
    "confidence": 0.95, "matched_by": "alias",
    "namespaces": ["prod-billing"], "owner_team": "team-billing" },
  { "service": "acquirer-gateway", "confidence": 0.6, "matched_by": "description" }
]
```

Возвращать до 5 кандидатов. Если уверенность лидера ниже 0.5 — вернуть всех и
пометить `ambiguous: true`, чтобы агент переспросил пользователя.

**`list_services(filter?) -> Service[]`**

Фильтры: `team`, `namespace`, `criticality`, `has_metadata`. Компактный вывод:
имя, title, команда, namespace. Нужен агенту для обзорных вопросов.

**`get_service_info(service) -> ServiceInfo`**

Карточка: метаданные, workloads, текущее состояние подов (running/desired), образ,
задеплоенный коммит, ссылки на репозиторий и раннбуки.

### Критерии приёмки фазы 1

- Индексер находит **не менее 90%** реально работающих сервисов кластера.
- Для сервисов с `service.yaml` заполнены владелец и алиасы.
- Тест: 20 реальных формулировок из чата инженеров (собрать заранее) →
  `resolve_service` даёт правильный сервис первым кандидатом минимум в 16 случаях.
- Индексер переживает недоступность GitHub: топология обновляется, метаданные
  остаются от предыдущего цикла.

## Фаза 2. Снапшот состояния

**Цель:** один вызов отвечает на 80% вопросов «что с сервисом».

### 2.1. Источники

- **Alertmanager** — активные алерты по сервису. Самый высокий signal-to-noise,
  подключать первым.
- **Kubernetes events** — за окно, с фильтрацией по подам сервиса. Здесь видны
  OOMKilled, ImagePullBackOff, FailedScheduling.
- **Состояние подов** — ready/total, счётчик рестартов, причина последнего
  завершения контейнера, возраст пода.
- **Prometheus** — метрики из `service.yaml` (`metrics[].promql`) плюс дефолтный
  набор golden signals, если метаданных нет: RPS, доля 5xx, latency p95, CPU,
  память, рестарты.

### 2.2. Базовая линия (обязательно)

Каждая метрика возвращается тремя точками:

```json
{
  "id": "success_rate", "title": "Доля успешных платежей", "unit": "ratio",
  "current": 0.31, "hour_ago": 0.98, "same_time_yesterday": 0.97,
  "delta_vs_yesterday_pct": -68.0,
  "anomaly": true
}
```

`anomaly` — простое правило (отклонение больше порога, порог в конфиге). Не строить
здесь ML: задача поля — расставить приоритеты для внимания модели.

### 2.3. Инструменты

**`get_service_snapshot(service, window="1h") -> Snapshot`**

Главный инструмент сервиса. Внутри — параллельные запросы ко всем источникам с
общим дедлайном (5 секунд), частичный результат при таймауте отдельного источника.

Структура ответа:

```json
{
  "service": "payments-api",
  "generated_at": "...",
  "health": "degraded",              // healthy | degraded | down | unknown
  "summary_hints": [                  // факты, а не выводы — выводы делает модель
    "3 из 6 подов в CrashLoopBackOff",
    "success_rate упал на 68% относительно вчера",
    "деплой 24 минуты назад"
  ],
  "alerts": [...],
  "workloads": [...],
  "pods": { "ready": 3, "total": 6, "restarts_1h": 14, "problems": [...] },
  "metrics": [...],
  "recent_events": [ /* Event, см. 1.2 */ ],
  "errors": []
}
```

`health` вычисляется детерминированно по правилам (есть critical-алерт → degraded;
ready == 0 → down; и т.д.). Модель не должна выводить это сама — правило должно быть
одинаковым от вызова к вызову.

**`query_metrics(service, metric_id? | promql?, window, step?) -> Series[]`**

Drill-down. Приоритет — `metric_id` из метаданных сервиса. Произвольный PromQL
разрешён как fallback, но с ограничениями: максимум окна, максимум числа
возвращаемых серий (20), максимум точек на серию (200). При превышении — ошибка с
объяснением, как сузить запрос, а не усечённый результат.

### Критерии приёмки фазы 2

- `get_service_snapshot` отрабатывает за ≤ 5 секунд на сервисе с 20 подами.
- При остановленном Prometheus снапшот возвращает k8s-часть и заполненный `errors`.
- На искусственно сломанном тестовом сервисе (OOM, неверный образ, падение
  зависимости) `summary_hints` содержит корректную причину во всех трёх случаях.

## Фаза 3. Логи

**Цель:** снапшот перестаёт говорить «сервис деградировал» и начинает говорить
«падает на connection refused к acquirer-gateway».

### 3.1. Объём

- Клиент Loki (query_range, labels API).
- Селектор берётся из `service.yaml` (`logs.selector`), при отсутствии —
  выводится из лейблов подов сервиса.
- **Агрегация паттернов** — ключевая часть, а не выдача сырых строк. Тысяча
  одинаковых ошибок должна прийти к модели как одна строка с counter. Реализация:
  нормализация строки (маскирование чисел, UUID, IP, timestamp) → группировка →
  top-N по частоте.

### 3.2. Инструменты

**`query_logs(service, level?, pattern?, window="1h", mode="patterns") -> LogResult`**

`mode`:
- `patterns` (по умолчанию) — агрегированные паттерны с примером и счётчиком;
- `raw` — последние N строк, N ≤ 100.

```json
{
  "mode": "patterns",
  "total_lines": 48213,
  "patterns": [
    { "count": 12043, "level": "error",
      "template": "dial tcp <IP>:<NUM>: connect: connection refused",
      "example": "dial tcp 10.42.1.7:8080: connect: connection refused",
      "first_seen": "...", "last_seen": "..." }
  ]
}
```

### 3.3. Интеграция в снапшот

`get_service_snapshot` дополняется полем `top_errors` — три верхних error-паттерна
за окно. Отдельного вызова для типового вопроса быть не должно.

### Критерии приёмки фазы 3

- Агрегация сжимает 10 000 строк логов до ≤ 20 паттернов.
- Запрос без селектора невозможен: инструмент отклоняет вызов без привязки к сервису.
- Ограничение окна и объёма выдачи Loki соблюдается (значения — в конфиге).

## Фаза 4. Изменения и таймлайн

**Цель:** отвечать на «что изменилось перед тем, как сломалось» — самый частый
реальный ответ на «что пошло не так».

### 4.1. Источники изменений

- **Деплои.** Смена `image` у workload. Индексер фазы 1 уже хранит `deployed_commit`;
  здесь добавляется история смен (таблица `deploy_history`).
- **Коммиты.** GitHub API: коммиты в ветку по умолчанию за окно — SHA, автор,
  сообщение. Плюс сопоставление с задеплоенным коммитом: какие коммиты смержены,
  но ещё не в проде.
- **Изменения конфигурации.** kusec API: изменения configmaps и env за окно.
  Интеграция уточняется после получения проекта kusec.
- **Алерты.** История срабатываний из Alertmanager.
- **Масштабирование и рестарты.** Из k8s events.

### 4.2. Обращение с секретами (жёсткое требование)

kusec содержит и configmaps, и secrets. Правила фильтрации применяются на стороне
`infra-mcp` до формирования ответа:

1. Значения secrets **не возвращаются никогда**. Только имя ключа и факт/время
   изменения.
2. Для env и configmaps: возвращается имя ключа всегда; значение — только если оно
   проходит allowlist-паттерн (URL, hostname, `svc.cluster.local`, булев флаг,
   числовой лимит). Всё остальное — `"***"`.
3. Ключи, чьё имя матчится на deny-список (`*PASSWORD*`, `*SECRET*`, `*TOKEN*`,
   `*KEY*`, `*DSN*`, `*CREDENTIAL*`), маскируются независимо от значения.

Реализовать как отдельный пакет `redact` с юнит-тестами. Порядок проверок:
deny-список имени → allowlist значения → маска.

### 4.3. Инструменты

**`get_timeline(service | services[] | scope="cluster", window="24h") -> Event[]`**

Все изменения на одной оси времени, отсортированные по убыванию времени, в
нормализованном формате из 1.2. Это второй по важности инструмент после снапшота.

**`get_changes(service, window) -> Changes`**

Детализация: список коммитов с авторами, диффы конфигурации (по ключам), история
деплоев. Для вопросов «покажи, что именно поменяли».

### Критерии приёмки фазы 4

- На тестовом сценарии (деплой → рост ошибок) таймлайн показывает деплой раньше
  первого error-события, с корректной временной дистанцией.
- Юнит-тесты `redact`: ни один секрет из тестового набора не проходит в вывод.
- Коммиты корректно сопоставляются с задеплоенным SHA; «в проде отстаёт на N
  коммитов» вычисляется верно.

## Фаза 5. Связи и внешний контур

**Цель:** отвечать на «а это точно наша проблема?» и «кого ещё задело».

### 5.1. Граф зависимостей

Строится из env через kusec: значения вида `http://acquirer-gateway.prod.svc:8080`
или `postgres://billing-db:5432` разбираются в рёбра графа. Резолвинг хоста в имя
сервиса — через каталог фазы 1 (k8s Service → workload → сервис).

Важно и должно быть отражено в описании инструмента: env даёт **сконфигурированные**
связи, а не фактический трафик. Для вопроса «включена ли интеграция» это точно; для
«кто сейчас реально ходит» — нет.

### 5.2. ruto (API-gateway)

- Список опубликованных наружу ручек сервиса.
- Домены, привязанные к сервису.
- RPS и коды ответов из метрик ruto — внешняя картина, в отличие от внутренних
  метрик сервиса. Расхождение между ними само по себе диагностический сигнал.

### 5.3. Инструменты

**`get_dependencies(service, direction="both", depth=1) -> Graph`**

`direction`: `upstream` (от кого зависит) | `downstream` (кто зависит) | `both`.
Для каждой связи — источник факта (`env` / `ruto`) и, при наличии, краткий статус
здоровья соседа (переиспользовать вычисление `health` из фазы 2, без полного
снапшота).

**`get_public_api(service) -> PublicAPI`**

Домены, опубликованные ручки, RPS и распределение кодов ответов за окно.

### Критерии приёмки фазы 5

- Граф строится минимум для 70% сервисов, имеющих зависимости.
- `depth=2` не приводит к взрывному росту ответа (ограничение на число узлов — 50).

## Фаза 6. Прокси к диагностическим ручкам сервисов

**Цель:** доступ к предметным данным, которых нет ни в какой инфраструктурной
телеметрии: зависшие записи в очереди, количество заявок в статусе, детали заказа.

Это самая ценная и самая рискованная фаза. Не начинать до завершения фаз 1–4.

### 6.1. Декларация

В `service.yaml`:

```yaml
endpoints:
  - id: stuck_queue_items
    title: Записи в очереди, зависшие дольше N минут
    path: /internal/diagnostics/stuck
    method: GET
    params:
      older_than_minutes: { type: int, default: 30, max: 1440 }
    max_rows: 50
    pii: []                       # поля, подлежащие маскированию
    timeout: 5s
  - id: order_details
    title: Детали заказа
    path: /internal/diagnostics/order/{id}
    method: GET
    params: { id: { type: string } }
    pii: [customer_name, phone, address, email]
    timeout: 5s
```

### 6.2. Требования безопасности

1. **Allowlist по `id`.** Модель не может передать произвольный путь. Только `id`
   из декларации, только объявленные параметры, только `GET`.
2. **Валидация параметров** по объявленным типам и границам до отправки запроса.
3. **Маскирование PII** по списку `pii` до попадания в ответ. Реализовать поверх
   пакета `redact` из фазы 4.
4. **Лимиты:** размер ответа, число строк, таймаут — из декларации, с жёсткими
   потолками в конфиге сервиса.
5. Вызов идёт на ClusterIP сервиса внутри кластера, без выхода наружу.

### 6.3. Инструменты

**`list_service_endpoints(service) -> Endpoint[]`** — что вообще можно спросить у
этого сервиса.

**`call_service_endpoint(service, endpoint_id, params) -> Result`** — вызов.

### Критерии приёмки фазы 6

- Попытка вызвать необъявленный путь или метод отклоняется.
- В ответе отсутствуют поля, перечисленные в `pii`, — проверено тестом.
- Недоступность целевого сервиса возвращает внятную ошибку, а не таймаут всего вызова.

## Фаза 7. Кластер и чат-интерфейс

### 7.1. Здоровье кластера

**`get_cluster_health(window="1h") -> ClusterHealth`**

Состояние нод, всплески потребления CPU/памяти, поды в проблемных состояниях по
всему кластеру, pending-поды, активные алерты уровня инфраструктуры. Отвечает на
вопросы вида «у нас всё лежит или только платежи».

### 7.2. Агент и бот

Отдельный компонент, не часть `infra-mcp`.

- Подключение к `infra-mcp` как MCP-клиент.
- Системный промпт: порядок диагностики (`resolve_service` → `get_service_snapshot`
  → при необходимости `get_timeline` / `query_logs` → drill-down), формат ответа,
  требование не выдумывать значения и явно сообщать о недоступных источниках.
- Транспорт: Telegram или Slack (по выбору заказчика).
- Проброс идентичности пользователя из чата в `infra-mcp` — обязательное требование.
  Без этого бот становится способом обойти существующий RBAC: сервис видит envs,
  логи и предметные данные всех сервисов сразу.

### 7.3. Проактивный режим (задел)

Алерт из Alertmanager триггерит тот же пайплайн, результат публикуется в канал
команды-владельца. Здесь основная ценность продукта: не «человек спросил», а
«разбор готов к моменту, когда человек открыл ноутбук». Проектировать фазы 1–4 так,
чтобы этот режим был вызовом тех же инструментов без переписывания.

## 9. Вопросы, требующие уточнения перед фазой 1

Задать заказчику при получении проектов манифестов и kusec:

1. Формат тегов образов: SHA коммита, семвер, или смешанный? От этого зависит
   реализация Р2.
2. Схема именования в registry и правила маппинга на репозитории GitHub.
3. Один кластер или несколько? Нужна ли поддержка мультикластерности в модели данных
   с самого начала.
4. kusec: API чтения env — по сервису, по namespace, по ключу? Есть ли история
   изменений с временными метками (нужно для фазы 4)?
5. Соответствие между сущностью в kusec и workload в кластере: по имени, по метке,
   иначе?
6. Есть ли трейсинг (Tempo/Jaeger) — влияет на фазу 5, граф зависимостей строился
   бы точнее.
7. Модель авторизации: откуда брать соответствие «пользователь чата → команда →
   доступные сервисы».
8. Какие LLM допустимы: внешний провайдер или self-hosted. Влияет на объём
   редактирования данных перед отправкой.
